# LOCKIN app audit (2026-11-14)

Scope: `frontend/` (Next.js 15 pages + API routes), the shared controllers in `frontend/backend/src`, and the live Supabase project (read-only checks). Nothing is committed or pushed.

**Verified:** `tsc --noEmit` is clean and `next build` passes. A group-flow harness drives the real controllers against an in-memory database: 12/12 checks pass, and it fails on the old code. Timer unit checks pass.
**Not verified:** no clicking through the running app. Testing against production would create real missions and notifications that other students would see, which breaks the no-fake-activity rule. Recap card visuals, the notification look and iOS behaviour need a check on a real phone.

## 2. Login and password reset

**Staying signed in.** The client config is already right: the session persists in localStorage, refresh tokens auto-refresh, and a single 401 never signs anyone out. The project also has no time-boxed or inactivity session limits (0 sessions with a hard expiry). The remaining real risk is **iPhone Safari's 7-day storage limit (ITP)**: if a student doesn't open lockin.top in Safari for 7 days, iOS can wipe its storage and they get signed out. Two ways round it:
- Students add LOCKIN to the Home Screen. Home Screen apps are exempt, and this also unlocks timer notifications on iOS.
- Long-term: move the session into a server-set cookie (`@supabase/ssr`). **Postponed:** it's a significant auth refactor, and there's no evidence yet of how often it happens.

**Accounts never lost.** Data check: 0 orphaned profiles and 0 duplicate emails. The one unlinked profile belongs to an unconfirmed signup and links on its first confirmed login. **Added a guard:** if an auth account is ever deleted and the same verified email signs up again, the old profile is re-linked instead of locked out with "linked to another account" (`lib/requireAuth.ts`).

**Password reset.** What changed:
1. `ProfileGate.tsx` now shows the real reset-email error. Supabase answers the same for unknown emails, so this reveals nothing about who has an account.
2. A recovery link that lands on `/` (because `/reset-password` isn't in the allowed Redirect URLs) is now forwarded to `/reset-password`, instead of quietly signing the user in (`lib/supabase.ts`).
3. **Skip for now** on both reset screens (the link page and the in-app 6-digit code step).
4. **Change password while signed in:** Profile → key icon (`ChangePasswordDialog.tsx`). This is also the fallback if email is broken.
5. "Cancel" on the code reset step now ends the recovery session, so a reload doesn't sign the user straight in.

**You (Supabase dashboard).** I can't read these settings from here. Check them, then request a reset and confirm `recovery_sent_at` gets set:
- Auth → URL Configuration: Site URL `https://lockin.top`; Redirect URLs include `https://lockin.top/reset-password` (plus `www.` if used).
- Auth → Emails → SMTP: custom SMTP is configured. Supabase's built-in sender only mails project team members, about 2 per hour.
- Auth → Email Templates → **Reset Password**: include `{{ .Token }}`, because the app promises a 6-digit code. Keep the link as well.

## 3. Group sessions: bugs found and fixed

| Bug | Effect | Fix |
|---|---|---|
| `cancelMission` called `notifyUser`, which doesn't exist | A host cancelling, or a participant leaving, got a 500. The participant's row was already deleted, so the UI showed an error after the action had happened. | Uses `notify()`. ## 4. Mobile timer
Root cause: the timer stored "seconds left" and counted down with `setInterval`. Locked screens and background tabs pause JavaScript, so ticks were lost. The restore code also re-ran on every 15 s refresh. **Now** (`lib/focusTimer.ts`): it stores start, pause and paused-total timestamps, and always computes time from the clock. It re-syncs on unlock, tab focus and bfcache restore. It restores once on load, and falls back to the server's `work_started_at` if storage was cleared. Countdowns freeze exactly at the target.
Notifications (`public/sw.js`, `lib/focusNotify.ts`): a persistent "LOCKIN · focus running · ends at 3:45 PM" notification while a session runs, and "session complete" when it ends. Tapping one opens the queue. The tab title shows the time on desktop.
**Honest limits:** iPhone has notifications only when LOCKIN is added to the Home Screen (iOS 16.4+); in a Safari tab, nothing shows. No browser can fire an exact-time alert while the page is frozen, so the "complete" alert fires when the page is awake or when the user returns. The running notification shows the end time for exactly this reason.

## 5. "Continue Focus" on a first-time preloaded mission
Root cause: starter quests (and solo missions from the create form) were created with the server default `startNow: true`. They were already "Executing", with the server clock running before the user tapped anything. That is why the card said "Continue focus", and the pre-tap minutes counted toward the session. **Fix:** these are now created with `startNow: false`, so the card shows **Start session** with the 25/45/90/open picker (was 25/50/90). The live card says "Start focus" until a timer exists for that mission, and a stale server start time is never used. Quick Focus still starts straight away, by design.

## 6. Recap card
Root cause of the black card: the modal opened in **Story Sticker** mode, whose background is transparent unless a screenshot exists. On the black overlay it rendered as a black card. **Now:**
- It always opens on the **Metallic** tier card.
- The top slider is Metallic / Sticker (transparent PNG) / Photo. The sticker style picker is kept, and the flip stays in the app.
- The Photo version has a strong text shadow, so text reads on any image.
- **Save PNG:** Card / Sticker / Photo, each exported separately, whatever is on screen. The dotted transparency preview grid was being baked into the "transparent" PNG; it is now excluded.
- Copy sticker is kept, and the Motion delta shows "−5" instead of "+-5".
